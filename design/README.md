## 小程序首页动态背景

源视频 `vibe_images/8be41300c22957ae44de3ad8ca03d776.mp4`：720×1280 · 24fps · 193 帧 · 8.04s · 999KB · **HEVC(H.265)**。
成品都在包里：`/asserts/video/home-bg.mp4`（H.264 · **32.00s 回文循环 @12fps** · 1197KB）与打底的 `/asserts/images/home/home-bg.jpg`（720×1280 · 317KB）。

### 为什么是「正放 + 倒放」而不是交叉溶解

被否过两轮的根因是**循环点被看成「播完重播」**，而交叉溶解本身就会制造这个 cue —— 它把末段运动量抽干，形成一次视觉收束。实测各方案末段每帧变化量（正常帧间均值 0.58、最大 3.20）：

| 收口方式 | 末段变化量 | 结果 |
| --- | --- | --- |
| 1.0s 溶解到首帧 | 1.03 → **0.04** | 近乎定格 1 秒，明确读作「播完」 |
| 0.33s 溶解到首帧 | 0.46 → 0.34 | 好一些，但仍被看出重播 |
| 回文（正放+倒放）16s | 折返处 **0.18~0.52** | 无收束、无定格，但仍被认出在重复 |
| **回文 + 慢放，32s 周期** | 折返处 0.19 | 当前采用 |

回文能用是因为这素材**没有方向性运动**：用 `cv2.phaseCorrelate` 量了 8.04s 内各区域的整体位移，天空 0.12px、瀑布 0.12px、云海 0.15px、湖面 0.49px、全画面 0.16px —— 全是原地闪点/明暗呼吸，倒放不穿帮。**换素材必须先重测这一项**，只要有肉眼可辨的平移或下落，回文就不能用。

**但回文只解决「接缝」，不解决「认得出是同一批事件」** —— 8 秒素材里那几个闪点爆发（第 90 帧那下最大，帧间 3.20）来回播，看久了就是能认出来。所以还要往下两招：，是全片最小的步长之一；编码后实测该处显示 3.45，那是首帧走 IDR、末帧走 P 链、两套独立量化噪声之差，仍落在素材自身正常步长（最大 3.20）范围内，不是画面位移。

### 拉长周期：降容器帧率就是免费慢放

同样 384 帧回文，用 12fps 承载就是 32 秒周期，事件密度直接减半；而且不用重复帧，比「每帧播两遍 + 24fps」还省 169KB。

| 构造 | 周期 | 体积 |
| --- | --- | --- |
| 回文 @24fps | 16.0s | 853KB |
| 回文·帧重复2次 @24fps | 32.0s | 1366KB |
| **回文 @12fps** | **32.0s** | **1197KB（取这档）** |
| 回文 @8fps | 48.0s | ~1150KB（更省周期更长，但闪点会开始跳） |

实测该档帧间 mean 0.52 / max 3.15、折返处 0.19、循环点 3.34 —— 循环点仍低于素材自身的正常最大步长，不是异常点。

### 随机起点：切 tab 不再重看开头

三个 tab 内容是 `wx:if` 互斥的，`menu` 每次切回都被重建，视频若固定从 0 起播，**切一次 tab 就重看一遍开头** —— 这是比循环点更常被看到的「重新播放」。
现在 `lifetimes.attached()` 每次挂载取一个 `0~BG_LOOP_SEC` 的随机值喂 `initial-time`。实测三次连续挂载分别是 20 / 9 / 6 秒，且 `bindplay` 每次都触发（说明随机起点确实起播了）。
随机起点与固定起点之间没有跳变问题：视频在 `bindplay` 之前一直是 `opacity: 0`，露出的是同素材的静帧。

### 出片参数

1. 帧序列 = `F + F[-2:0:-1]` → 193 + 191 = **384 帧 = 16.00s @24fps**（去掉重复端点，折返处才是正常步长）。
2. 帧在 Python 里算好后以 `rawvideo/bgr24` 管给 ffmpeg：`-c:v libx264 -preset slow -pix_fmt yuv420p -profile:v high -level 4.0 -tune film -an -movflags +faststart`。
3. crf 扫描：29 → 1129KB、30 → 981KB、**31 → 853KB（取这档）**、33 → 656KB。crf31 对源帧平均绝对误差 3.85/255，云海渐变区灰阶 177（源 170），无分层；crf33 起开始糊细小闪点。
4. 源是 HEVC，安卓解码不稳，必须转 H.264。OpenCV 的 `VideoWriter` 出不了 H.264（缺 openh264.dll，只有 `mp4v`，微信不认），必须用 ffmpeg：`C:\Users\zhou\AppData\Local\Microsoft\WinGet\Links\ffmpeg.exe`。

### `<video>` 的三个坑

| src 写法 | 实测 |
| --- | --- |
| 包内路径 `/asserts/video/home-bg.mp4` | **整块黑**，连 `.bg` 的渐变底都被盖住。官方只列「网络路径 / 本地临时路径 / 云文件ID」 |
| 用户目录临时路径 `http://usr/home-bg-p16s.mp4` | **正常播放**（开发者工具已验证） |

`resolveBgVideo()` 因此把包内母本 `readFileSync` + `writeFileSync` 到 `wx.env.USER_DATA_PATH`。
**临时文件名必须带版本戳**（`BG_MP4_TMP_NAME = 'home-bg-p32s.mp4'`）：`accessSync` 命中就跳过复制，换视频不改这个名字，真机会一直播老素材 —— 这个坑踩过一次。有 CDN 就填 `BG_CDN`，优先级最高且省掉复制。

**切 tab 会闪一下黑**：首页三个 tab 内容是 `wx:if` 互斥的，切走时 `menu` 整个销毁，切回时 `<video>` 重建、在首帧解码出来之前先画一帧黑，而它盖在静帧上面。实测这段空窗有 20 次取数往返那么长（约 300~800ms）。
解法是 `bgLive` 开关：视频默认 `opacity: 0`，`bindplay` 触发后才淡入（420ms），空窗期由同素材同 cover 裁切的静帧顶着，构图不位移，所以看不出来。
验证方式：临时把 `onBgPlay` 里的 setData 注掉冻结空窗，量得背景区均值 168（正常画面）而不是黑。

### 打底静帧参数

取全片拉普拉斯方差最高的一帧（min 910 / 中位 988 / **max 1045 → 第 16 帧**），`unsharp(amount 0.55, radius 2.2)` 后存 JPG q90。显示后（780×1688）锐度：原帧 375 → 锐化后 **805**；预放大到 1080×1920 再锐化只有 781 且多 206KB，所以不预放大，交给 `aspectFill` 插值。它同时负责视频出画前不闪黑、以及真机播不了时的兜底画面。

### GIF 方案（已废弃，留参数）

`<image>` 吃包内路径所以 GIF 一定能播，但 8s 整段要 5~9MB，只取得 2s 窗口（400×712 · 16 帧 · 256 色 · 1044KB，接缝 1.94），**2 秒周期循环感太明显**。要点备查：必须全局调色板（逐帧独立板会从 659KB 涨到 3.9MB）；`paletteuse` 的选项名是 `dither` 不是 `dither_method`，且开 dither 体积翻倍；**别让 ffmpeg 自己 `fps=N` 采样**，会漏掉收口帧，接缝从 1.9 涨到 2.6~2.9。

### 「十二星座」横幅切图

预乘 alpha 后 LANCZOS 缩到 750 宽（避免云缘彩噪），再 `bilateralFilter(7,28,28)` 保边去噪，**保留 alpha 通道**存 PNG-32（254 级 alpha，61.8% 像素半透）= 431KB。卡片 686×258rpx（2.65:1）`aspectFill`，上下各裁 12%，标题与星盘完整。上一版把透明区回填成不透明底出 JPG（84KB），代价是卡片下缘出现一道暗边、云缘化不开 —— 已废弃。
